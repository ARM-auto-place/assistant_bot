# CI и релизы: assistant_bot

## Проверки

`ci.yml` (ML service CI) запускается на pull request и push в настроенные ветки. Выполняются проверки проекта и сборка Docker-образа linux/amd64 без публикации. PhotoAdvisor также запускает Node-тесты интерфейса.

## Релиз по тегу

Как в `db_migrations`, `release.yml` запускается при push тега `v*`, например `v1.2.0`. После успешных проверок образ собирается и публикуется в GHCR:

- `ghcr.io/arm-auto-place/assistant_bot:v1.2.0`
- `ghcr.io/arm-auto-place/assistant_bot:sha-<полный SHA коммита>`

Workflow заканчивается публикацией. Подключения к серверу, запуска Compose и задачи deploy нет ни в CI, ни в релизе. Обновление сервера выполняется отдельно с выбранной версией образа.

Создавайте новый тег на нужном проверенном коммите, содержащем `release.yml`, и отправляйте его отдельно:

```bash
git tag -a v1.2.0 -m "Release v1.2.0"
git push origin v1.2.0
```

Локальное создание тега без push ничего не запускает. Имя должно быть Docker-совместимым: `v` и от 1 до 127 букв, цифр, точек, дефисов или подчёркиваний. Теги вроде `v1.2.0-rc.1` тоже публикуют образ. Для нового релиза используйте новый номер; не переносите опубликованные теги на другие коммиты.

## Доступ к GHCR

Для публикации используется встроенный `GITHUB_TOKEN` с `packages: write`. Организация должна разрешать Actions и запись пакетов; существующему GHCR-пакету нужно дать доступ этому репозиторию. Дополнительный персональный токен не требуется.

Environment `production`, SSH-секреты и параметры сервера для этих workflow не нужны. Для скачивания приватного образа на сервере отдельно настройте доступ к GHCR с правом `read:packages`. Настройки приложения и модели подготавливаются отдельно от сборки образа.

## Запуск API

`compose.yaml` содержит PostgreSQL; `compose.api.example.yaml` — пример API-сервиса. Задайте `ASSISTANT_IMAGE` на опубликованную версию и настройте `.env`, сеть и подключение к БД. Внутри контейнера адрес БД должен указывать на доступный сервис/хост, а не localhost контейнера.

Dockerfile устанавливает `requirements-core.txt` без Torch. Индексация эмбеддингов требует отдельных зависимостей; база и FAQ подготавливаются отдельно. `/health` проверяет HTTP-процесс, а не доступность БД/DeepSeek.
